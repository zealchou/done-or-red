# 三軌檢查表：TDD／BDD／GDD

三軌問的是三個不同的「對」。合併成一句「有沒有測試」會漏掉另外兩軌——
一批東西完全可能「零件對、使用者卻沒拿到、圖也是假的」，三個都要分開問。

| 軌 | 問什麼 | 失敗長什麼樣 |
|---|---|---|
| **TDD** | 零件本身對不對 | 永遠是綠燈的測試——把實作拿掉，測試也不會紅 |
| **BDD** | 使用者真的拿到他要的了嗎 | 所有零件測試都綠，但正式使用流程裡沒有任何東西會呼叫到它 |
| **GDD** | 圖（系統之間怎麼接）是不是真的 | 圖描述的是一個已經不存在、或從沒真正接上的系統，而沒有人會發現 |

三題可以一個綠兩個紅，所以檢查的時候要逐條走，不能只看其中一軌就收工。

## 軌一：TDD——零件對不對

- [ ] 這條測試斷言的對象，是不是被測的那一個？（不是「清單裡隨便一個符合的元素」）
- [ ] **拔除演練**：把被測的實作拿掉或改壞，這條測試會不會變紅？
      不會紅 ⇒ 這條測試是裝飾品，不是保護網。
- [ ] 陽性對照：故意餵一個已知會失敗的輸入，測試真的抓到了嗎？
      （抓不到代表工具本身壞了，不是「剛好沒有問題」。）

## 軌二：BDD——使用者真的拿到他要的了嗎

- [ ] 把這批東西擺回「使用者從頭到尾會做的事」裡走一遍，不是只呼叫函式本身。
- [ ] 找出正式使用路徑裡，真的會呼叫到這個新零件的那一個入口。
      找不到入口 ⇒ 零件測試全綠也沒有意義，這是「零呼叫端」陷阱。
- [ ] 場景寫成「一個具體的人，在什麼情境下，想要什麼結果」，不要寫成函式清單。

## 軌三：GDD——圖是不是真的

完整方法論見 [`docs/gdd.md`](./gdd.md)（圖驅動開發），這裡只列檢查表：

- [ ] 圖描述的是**現況**（current-state），不是還沒蓋的設計藍圖。
- [ ] 從圖上挑兩個具體斷言回程式碼實測：一個「圖說存在的東西」真的存在嗎？
      一個「圖說會這樣流」的路徑，真的打一次，回應符合圖嗎？
- [ ] **拔除演練**：把圖上這批新加的模組從系統裡移除，其他部分的測試還會全綠嗎？
      全綠 ⇒ 這個模組是幽靈，圖上畫的接線根本沒被用到。
- [ ] 圖是不是唯一正本？如果有第二份（投影片、舊版文件），改完之後兩邊會不會兜不起來？
      判準：**如果有人只讀其中一份、不讀正本，他會拿到哪個版本？**

## 三軌一起用的順序建議

1. 開工前：GDD 的「圖在哪、圖是不是現況」先確認，避免蓋在假設之上。
2. 施工中：TDD 逐個零件紅→綠。
3. 收工前：BDD 走一遍使用者路徑，GDD 對帳圖與程式，三者都做完才算收工。
