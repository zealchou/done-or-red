# 三軌檢查表：TDD／BDD／GDD

三軌問的是三個不同的「對」。合併成一句「有沒有測試」會漏掉另外兩軌——
一批東西完全可能「零件對、使用者卻沒拿到、圖也是假的」，三個都要分開問。

| 軌 | 問什麼 | 失敗長什麼樣 |
|---|---|---|
| **TDD** | 零件本身對不對 | 永遠是綠燈的測試——把實作拿掉，測試也不會紅 |
| **BDD** | 使用者真的拿到他要的了嗎 | 所有零件測試都綠，但正式使用流程裡沒有任何東西會呼叫到它 |
| **GDD** | 圖（系統之間怎麼接）是不是真的 | 圖描述的是一個已經不存在、或從沒真正接上的系統，而沒有人會發現 |

三題可以一個綠兩個紅，所以檢查的時候要逐條走，不能只看其中一軌就收工。

## 軌一：TDD——零件對不對

- [ ] 這條測試斷言的對象，是不是被測的那一個？（不是「清單裡隨便一個符合的元素」）
- [ ] **拔除演練**：把被測的實作拿掉或改壞，這條測試會不會變紅？
      不會紅 ⇒ 這條測試是裝飾品，不是保護網。
- [ ] 🔴 **拔除演練要講得出「哪個看得見的行為變了」。**
      「我改了那個檔案」不等於「我改到了那個行為」——
      一刀有可能落在一個根本到不了的分支上，或被上游的檢查提前擋掉，於是那一刀什麼也沒動。
      ⇒ **0 紅的時候，第一個假設是「這把刀壞了」，不是「這批測試瞎了」。**
      要證明測試真的瞎，先換一把**已知有效**的刀再量一次。
- [ ] **要數「是哪幾條紅」，不是只看有沒有紅。** 該紅兩條只紅一條，就是訊號。
- [ ] 陽性對照：故意餵一個已知會失敗的輸入，測試真的抓到了嗎？
      （抓不到代表工具本身壞了，不是「剛好沒有問題」。）
- [ ] 🔴 **陽性對照本身也會是假的。** 如果你餵進去的那個差異，在抵達被測的那一點之前
      就被截斷、四捨五入或轉換掉了，你等於拿同一組輸入去比它自己——**恆綠，零證明力**。
      ⇒ 先確認**那個差異真的抵達了被測點**，再相信對照的結果。

## 軌二：BDD——使用者真的拿到他要的了嗎

- [ ] 把這批東西擺回「使用者從頭到尾會做的事」裡走一遍，不是只呼叫函式本身。
- [ ] 找出正式使用路徑裡，真的會呼叫到這個新零件的那一個入口。
      找不到入口 ⇒ 零件測試全綠也沒有意義，這是「零呼叫端」陷阱。
- [ ] 場景寫成「一個具體的人，在什麼情境下，想要什麼結果」，不要寫成函式清單。

## 軌三：GDD——圖是不是真的

完整方法論見 [`docs/gdd.md`](./gdd.md)（圖驅動開發），這裡只列檢查表：

- [ ] 圖描述的是**現況**（current-state），不是還沒蓋的設計藍圖。
- [ ] 從圖上挑兩個具體斷言回程式碼實測：一個「圖說存在的東西」真的存在嗎？
      一個「圖說會這樣流」的路徑，真的打一次，回應符合圖嗎？
- [ ] **拔除演練，一次要看兩件事**（只看一件會得到相反的結論）：
      ① **這個模組自己的驗收必須變紅。** 沒變紅 ⇒ 它是幽靈，圖上畫的接線根本沒被用到。
      ② **跟它不相干的其他測試應該維持綠。** 跟著紅 ⇒ 那條紅線就是耦合的位置。
      🔴 ①和②問的是兩個不同的問題：**「它到底有沒有被用到」** vs **「它拆不拆得乾淨」**。
      只記得其中一件，就會把「其他測試全綠」同時讀成好事和壞事。
      （[`gdd.md`](./gdd.md) 的 A3 只問②，所以那裡寫「其他層必須全綠」是對的。）
- [ ] 圖是不是唯一正本？如果有第二份（投影片、舊版文件），改完之後兩邊會不會兜不起來？
      判準：**如果有人只讀其中一份、不讀正本，他會拿到哪個版本？**

## 🔴 三軌裡最容易被漏掉的一格：跑測試時，對方是你寫的替身

三軌都成立，但它們**最常被執行成的那個版本**有一個共同的隱形前提：
**跑測試的時候，對方是你寫的替身。**

只要有一個數字、欄位或狀態是**送出去給別人收的**（另一個服務、別的團隊的 API、
雲端供應商、瀏覽器），**替身就驗不到它**——因為**替身寫進去的是你以為的對方規則，
而假的那個不會拒絕**。

🔴 **這一格不在三軌之外，它在三軌裡**：它就是 GDD 那條「真的打一次、看回應符不符合圖」
延伸到跨系統邊界的版本。**整合測試、契約測試、部署煙霧測試都會紅**——
驗不到的只有「對方是替身」那一種。

- [ ] 這批有沒有任何值是送出去給別人收的？沒有 ⇒ 跳過這一節。
- [ ] 有的話：那個值是從**對方的正式說明**查來的，還是憑印象寫的？
- [ ] 查不到的那一格，有沒有**誠實留白**（而不是填一個看起來合理的數字）？
- [ ] 這一格是怎麼驗的？**「對方是替身」的那種測試不算**——要嘛真的往對面送一次
      （這是會紅的測試，通常掛在部署那一關而不是每次提交），
      要嘛啟動時向對方問出來，要嘛誠實標示「沒有東西在守，把關者是人」。

完整版（三題自問、三種驗法、一個旋鈕被兩個用途共用的變形、跨檔案的鏈與它的控制單元）
見 [`docs/cross-system-numbers.md`](./cross-system-numbers.md)。

## 三軌一起用的順序建議

1. 開工前：GDD 的「圖在哪、圖是不是現況」先確認，避免蓋在假設之上。
2. 施工中：TDD 逐個零件紅→綠。
3. 收工前：BDD 走一遍使用者路徑，GDD 對帳圖與程式。
4. **三軌走完之後，把每一條驗收條件填進 [`evidence-ledger.md`](./evidence-ledger.md)**，
   標清楚哪一格是機器驗的、哪一格只有人驗得了。
5. 要給別人用之前，走 [`launch-card.md`](./launch-card.md) 十二項。

## 🔴 三軌全綠之後還缺的那一層

**三軌問的都是「機器能不能證明它對」。** 三軌全綠而使用者說「這不是我要的」，
三軌沒有一條會紅——因為**「是不是他要的那個」沒有可執行的判準**。

⇒ 三軌是必要條件，不是充分條件。那一層在
[`evidence-ledger.md`](./evidence-ledger.md)〈哪些一律是「人」〉那張表裡，
而它的規矩是：**人那一格空著的時候，就算所有機器那一格都綠了，整批不算完成。**
