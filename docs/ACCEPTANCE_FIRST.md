## 三、怎麼算做完（寫成可執行的那一行，而且現在應該是紅的）

**那一行**：

```
bash scripts/test-scan.sh
```

**開工時的狀態**：🟢 17 項全綠——所以**它當時證明不了本批任何一件事**。

⇒ **本批的第一個動作是讓它變紅**：先加上第 1、2 項的測試（那時 `install.sh` 與
`pre-commit` 還不存在，測試必須紅），再動手寫它們。
**先看到紅，才有資格相信後來的綠。**

**收工時的狀態**：🟢 44 項全綠，經三輪獨立覆核與十七把刀的拔除演練。

**每一項的驗收條件（缺一不算做完）**：

🔴 **E3、F2、F4b 必須跟 E2、F1、F4 同一批存在。** 只驗正向的話，「把每一個提交都擋下來」
也會滿分——而那種閘門的真實結局是使用者把它刪掉。

🔴 **F3 與 E13a 的實測記錄：只砍一處會得到 0 紅**，因為它們被兩到三處程式碼守著。
**0 紅的第一個嫌疑人是刀，不是測試**——這兩次都確認是刀不夠，全砍才紅。

🔴 **但 0 紅也可能真的是測試有洞**：E12 第一次拔除演練 0 紅，查下去發現它只測了
「完全不相關的閘門」，沒測「使用者把兩邊併在一起」那種——那才是兩種身分判斷法
行為不同的地方。**補了 E12b 之後，同一把刀恰好紅 1 條。**
⇒ 判準：**0 紅先懷疑刀；刀確認砍到了，就換懷疑測試的覆蓋範圍。兩個都要查。**

**使用者視角的驗收（BDD，不准出現任何內部檔名）**：

- **G**iven 一個完全沒有程式基礎的人，剛開了一個新資料夾要做他的產品
  **W**hen 他叫他的 AI 助手「把這套規矩裝進來」
  **T**hen 他不必知道任何指令，就看到 AI 回報「裝好了，現在有 X 在守著」
- **G**iven 他的 AI 不小心把一組密碼寫進檔案
  **W**hen AI 要把這批改動存起來
  **T**hen 它被攔下來，而且**AI 自己看得懂為什麼**、自己去把密碼拿掉；
  這個人只會看到 AI 跟他說「我剛才差點把密碼存進去，已經處理掉了」
- **G**iven 他換了另一個 AI 助手
  **T**hen 規矩照樣生效（因為安裝時四家的檔名都放好了）

- **新增生產碼上限 200 行**（bash）。超過就停下來回報，不准自己放寬。
  估計：安裝 80、閘門 60、測試 40。
- **新增檔案上限 4 個**（上表第 1～4 項）。要第 5 個必須先講理由。

  才跑得動的東西，對目標使用者等於不存在。

而「估計差了多少」本身是這個包在教的東西。

wc -l <檔案>                        # 現在

🔴 **原本這張表寫的是 370／203／+113，三個數字都不成立**——因為我混用了
「逐筆提交的新增行數」與「整段範圍的淨增」兩種算法，而且報給擁有者的時候還先講了
一個更小的估計值。教訓：**報一個數字之前，先寫下「這個數字是怎麼算的」那一行指令。**
算法沒寫下來的數字，過幾天連自己都重現不出來。

**破了之後做了什麼**：停下來把兩個數字回報給擁有者，並把理由寫下來（下面這段），
**沒有自己把上面那三行的數字改大**。他同意照這個方向做完。

**為什麼會差 2.1 倍**（不是為了辯解，是為了下一次估得準）：
- 🔴 **最大單一原因：第三輪覆核推翻了「工具放在哪」這個地基決定。**
  前兩輪都在補洞，第三輪才看出五條阻塞是同一個病——**閘門用「它正在檢查的那個
  資料夾裡的東西」來證明自己是好的**。改掉地基比補洞貴，但補洞永遠補不完。
- 估的時候只算了「把東西放好」，沒算「放不成功的時候要怎麼講」。誠實回報的程式碼
  跟做事的程式碼差不多長——安裝腳本 218 行裡，約 60 行在處理失敗、撞名與「裝了但沒執法」。
- 三輪覆核共抓出 13 個阻塞級缺陷，多數修法是**加防線**，不是改字：
  檢查暫存區而非工作目錄、要求檢查工具交出結果行、把「搜尋出錯」跟「沒找到」分開、
  暫存檔與列舉檔案的失敗也要分開、名單不覆蓋、失敗時退出非 0、把 python3 換成 sed、
  閘門身分改成逐位元組比對。

**馬尾回頭審（423 行，已過 400 行檢查點）**：
- 🔴 `delete`：**刪掉了一整組規則**——原本抓 `password = 一串東西` 的那組（含它的
  佔位符濾清單）。三輪覆核各生一個新洞，根因是「這串字是真密碼還是教學範例」
  是**判斷題**，而正規表達式沒有判斷力。改成看檔名的規則，不需要判斷。
  **這是本批唯一一次程式碼往下走。**
- `native`：四處改用平台原生機制——`git checkout-index` 取出要存進去的那一份、
  `git rev-parse --git-path hooks` 問閘門資料夾在哪、`git rev-parse --git-dir`
  找一個版本控制碰不到的地方放工具、`sed` 取代 python3。
  這四處都是**把自己寫的判斷刪掉、換成 git／shell 自己知道的答案**。
- `shrink`：三段各約 10 行的重複檢查邏輯收成一個 `scan_one()`，各剩 1 行。
- `yagni`：金鑰特徵裡的 Slack／Google 兩種格式只是既有規則裡多兩個選項，沒有新結構，留。
- 🔴 **審完的結論**：423 行裡最該檢討的不是長度，是**前兩輪有 200 多行花在補一個
  地基錯了的設計上**。判準：**同一層連續兩輪被抓到問題，第三輪不要再看個別缺陷，
  先問這些缺陷有沒有同一個根因。**

## 🔴 誠實標示：本批做不到的事

| 做不到的 | 為什麼 | 誰把關 |
|---|---|---|
| 閘門在「AI 寫檔案的當下」就攔住 | 那需要各家 AI 助手自己的機制，每家不一樣 | 無人；已寫成已知限制 |
| 使用者從來不存版本的話，閘門永遠不觸發 | 閘門掛在版本控制那一步 | 無人；已寫成已知限制 |
| 「給 AI 的指示」有沒有被照做 | 沒有任何機械判得了 | 人 |
| 規則檔裡那八條核心判準，AI 會不會真的遵守 | 同上 | 人 |
| 自己發明格式的秘密（被切成兩半、自訂前綴） | 金鑰檢查只認得列出來的那幾種形狀 | 人；已寫成已知限制 |
| `password = 你自己想的字串` | **刻意不做**：那是判斷題，三輪覆核證明規則兩個方向都會錯 | 人；改用檔名規則降低風險 |
| 把真的密碼檔改名成 `secrets.example` 再存進去 | 範本豁免是按檔名給的，按檔名就繞得過 | 人；這是換來「不誤擋正確做法」的代價 |
| 換一台電腦或別人抓下專案後，保護不會自動跟著來 | 工具放在版本控制碰不到的地方（那正是它安全的原因） | 人；安裝訊息會講，要再跑一次安裝 |

**這八項在任何回報裡都不得講成「已經有東西在守」。**
