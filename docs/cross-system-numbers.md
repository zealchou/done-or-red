# 跨系統那一格：三軌裡最容易被漏掉的那一格

TDD 問零件對不對，BDD 問使用者拿到了沒，GDD 問圖是不是真的。
三軌都成立，但它們**最常被執行成的那個版本**有一個共同的隱形前提：
**跑測試的時候，對方是你寫的替身。**

只要有一個數字、欄位或狀態是**送出去給別人收的**——另一個服務、另一個團隊的 API、
雲端供應商、瀏覽器、作業系統——那一格就落在**替身驗不到的地方**。

🔴 **這一節刻意不說「三軌之外」**（第一版寫錯了，改在這裡講清楚）：
它**不在三軌之外，它在三軌裡**，是需要**跨邊界取證**的那一格。
整合測試、契約測試、部署煙霧測試**都是測試，而且真的會紅**——本節第三節就在講怎麼讓它紅。
真正驗不到的只有一種：**只在你家跑、而且對方是你自己寫的替身的那種測試。**

## 一、為什麼替身驗不到

> **測試裡的對方是假的，而假的那個不會拒絕。**

你為那個外部服務寫了一個替身（stub／mock／fake）。你寫替身的時候，寫進去的是
**你以為對方的規則**。所以：

- 你猜的上限是多少，替身就接受多少。
- 你猜錯一個數量級，替身**也照樣回你 200**。
- 你的測試套件會全綠，而且綠得很有說服力。

這不是測試寫得不好，是**替身這個工具結構上證明不了這件事**。
**再多寫幾支同一種測試不會改善它**，只會讓你更有信心——
要改善它，得換一種取證方式（第三節）。

## 二、三題自問（動手改任何一個數字之前）

**Q1｜這個數字會被送出去給誰收？**

答案是「沒有人，它只在我家用」⇒ 三軌就夠了，往下不用看。
答案是任何一個名字 ⇒ 繼續。

**Q2｜我讀過那個收件人的正式說明了嗎？**

🔴 **憑印象、憑「上次好像是這個數字」、憑別人口頭轉述——一律不算。**
要讀的是原廠文件，或對方程式裡那個上限常數本身。
讀到之後，**把出處和數字一起寫進註解**，不要只留數字——
下一個人才知道這個數字不是你發明的，也才知道去哪裡確認它有沒有變。

**Q3｜查不到怎麼辦？**

🔴 **誠實留白。** 寫「這一格未經查證，不得當設計依據」，然後**真的不要拿它當依據**。

填一個看起來合理的數字，是這整份文件要防的那件事。
它的代價不是「數字錯了」，是**那個數字會被後面的人當成事實，長成規則**（見下面第四節）。

## 三、這一格能怎麼驗（三條，都不是「對方是替身」的那種測試）

替身驗不到，不等於沒辦法驗——**下面前兩條都是真的會紅的測試**。按可信度排序：

1. **真的往對面送一次**（部署檢查／smoke test）。這是唯一的直接證據。
   代價是它需要真的環境、真的憑證，通常不能跑在每次提交上——
   所以它是**部署閘門**，不是單元測試。
2. **啟動時向對方問出來**（如果對方有回報自己限制的端點）。
   好處是它永遠不會過期；壞處是對方不一定提供。
3. **把限制寫在旁邊當誠實標示**，並指名把關者是人。
   這是最弱的一種，但**比假裝有測試在守好得多**。

🔴 **不要用第 3 條冒充第 1 條。** 寫了註解不等於有東西在擋。
判準：**如果對方明天把上限改小一半，什麼東西會變紅？** 答不出來 ⇒ 現在沒有任何東西在守。

## 四、同一個病灶的另一種長法：一個旋鈕被兩個用途共用

這一節看起來像別的問題，其實是同一個。

**形狀**：有一個常數，原本是為第一種呼叫端校準的。後來第二種呼叫端出現了，
**它沿用了同一個常數**，因為那個常數「看起來就是在講這件事」。

**為什麼危險**：兩種用途的合理值常常差**一個數量級**，而沿用的時候沒有人重新量過。
於是那個常數對第一種用途剛好，對第二種用途小十倍或大十倍——**而且兩邊都不會報錯**。

**看到就問這兩題**：

- **它原本是為誰校準的？**（去翻它被加進來的那一次改動，看當時在解什麼問題）
- **新來的這個用途，跟原來那個差幾個數量級？**

**接著要先判一題，這一題不能跳**（第一版漏了它，寫成無條件規則，會製造第二個正本）：

> **這兩個用途，是同一件事實的兩種用法，還是兩件不同的事實？**

| 判定 | 怎麼修 | 為什麼 |
|---|---|---|
| **同一件事實**（同一個外部限制、同樣的生命週期、同一個收件人） | **一個正本，兩個投影。不准拆。** | 拆成兩個旋鈕 ＝ 同一筆事實有兩個家，兩邊會各自漂移，而漂移沒有人會發現。 |
| **兩件不同的事實**（不同收件人、不同的「多久算太久」、不同的失敗語意） | **兩個具名旋鈕，各自寫出自己的不變量。** | 它們本來就不該共用；共用只是因為名字看起來像。 |

🔴 **判定是「兩件不同的事實」之後，修法才是兩個旋鈕，而不是把同一個旋鈕轉大。**
把旋鈕轉大能讓新用途通過，代價是**舊用途從此失去它的保護**——
而舊用途沒有人在看，所以你不會知道自己弄壞了它。

🔴 **這一題怎麼判，沒有腳本判得了**（同一個常數在不同批次裡可能是同一件事、可能不是）。
答不出來就**兩個都寫下來給人看**，不要自己選一個然後往下走。

## 五、一條鏈上的數字，要有一個控制單元

當同一件事情的上限散在好幾個地方（前端顯示多久、中間層等多久、後端算多久、
外部服務願意等多久），這是一條**鏈**，不是幾個獨立的數字。

🔴 **這條鏈最難的地方**：鏈上的參與者**彼此可以完全沒有程式上的引用關係**。
它們住在不同檔案、不同語言、不同倉庫，名字也各不相同
（`timeout`／`deadline`／`budget`／`expires`／`max_*` 全都是同一件事的別名）。
⇒ **用「誰引用了這支檔」的方式探勘，永遠查不到它們是同一條鏈。**

**怎麼找**（找語意上的兄弟，不是找同一個名字）：

- **找同義詞**，不是找同一個字。
- **找同一個單位**——秒與毫秒混用的時候特別容易漏（`60` 對上 `10000` 看起來毫無關係）。
- **找跨語言、跨倉庫的那一半**——最關鍵的那個上限常常住在別人家，你怎麼查都查不到。

**找到之後，建一個控制單元。** 控制單元不是新模組；
**最小版本是一條寫出排序不變量的斷言**，例如「最外層 ≥ 中間層 ≥ 最內層」。

它的關鍵性質是：**它不住在任何一支參與的檔案裡。**
它讀那幾支檔取出數字，然後斷言它們的關係。這樣任何一支被改壞，它就紅。

🔴 **它要誠實標示自己驗不到什麼**：這種斷言驗的是**排序對不對**，
**驗不到「夠不夠大」**——夠不夠大取決於實際要跑多久，那要量，不是斷言得出來的。

## 六、這一節刻意不做的事

- **不給任何具體秒數、上限或門檻。** 那些數字屬於你自己的收件人，這份文件不可能知道，
  而**寫進來就等於製造下一個憑印象沿用的來源**——那正是本文件要防的事。
- **不提供自動偵測「這個數字有沒有收件人」的腳本。** 那是判斷題：
  同一個常數在不同批次裡可能有收件人、可能沒有，沒有腳本判得了。把關者是人。
- **不主張「只要有一次真的送過就永久有效」。** 對方的限制會變，而它變的時候不會通知你。

## `enforced_by`

| 規則 | 機械擋得住嗎 |
|---|---|
| 排序不變量（最外 ≥ 中間 ≥ 最內） | 🟡 **可以做成**一條斷言，改壞就紅——但**這個工具包裡沒有這條斷言**，它住在你自己的專案。**在你真的寫下它之前，這一列是 `model_obligation`，不是綠燈。** |
| 真的往對面送過一次 | 🟡 可以做成部署閘門，但不能放進每次提交 |
| 「同一件事實還是兩件事實」這一題怎麼判 | 🔴 沒有腳本判得了 |
| **有沒有人去找那條鏈** | 🔴 沒有腳本判得了 |
| **那個數字是不是真的從對方文件查來的** | 🔴 沒有腳本判得了。註解裡的出處可以是編的 |
| **留白的那一格有沒有真的被當成留白** | 🔴 沒有腳本判得了 |

🔴 **所以這一整份文件大部分是 `model_obligation`（對人是「紀律」）**，不是機械強制。
**不得宣稱本節已被系統強制。** 把關者是施工者自己與獨立審計。
