# GDD｜圖驅動開發（Graph-Driven Development）

> **收錄說明**：這份文件是這個工具包唯一直接搬過來、不是新寫的一塊——它原本是作者
> 自己內部工具鏈裡的一份方法論筆記，本身就已經自足、只引用公開來源、不含任何專案內容，
> 所以直接收錄，只做了兩處必要的去識別化（見文末〈收錄時的兩處刪節〉）。
> 內文偶爾會提到「姊妹文件」（棕地安全改動、幽靈接線稽核等），那些文件屬於作者的私有
> 工具鏈，**沒有一併收錄在這個包裡**——讀到那些引用時，代入你自己專案裡對應的方法論即可，
> 不影響 GDD 本身的三個判準與六道自問。

不是新方法論，是給一個既有紀律一個叫得出來的名字——叫得出名字的東西才傳得下去、
才能寫進派工單、才會被人想起來。

## 一、它到底是什麼（一句話）

**先畫好系統之間的網路圖，照圖開發；圖是唯一正本，改程式必須同批改圖。**

四個組成零件都有既有名稱，**本文不宣稱概念原創**：

| 零件 | 既有名稱 | 出處 |
|---|---|---|
| 所有 input／output 走統一控制單元 | 六角形架構／埠與轉接頭（Ports & Adapters） | Alistair Cockburn |
| 每個系統可熱插拔、不影響本體 | 微核心／插件架構（Microkernel） | 作業系統設計 |
| 圖先行 | C4 模型、模型驅動架構 | Simon Brown／OMG |
| 圖要能擋住違規，不只是掛牆上 | 架構適應度函數（fitness functions）＋ ArchUnit | 《Building Evolutionary Architectures》2017 |

**查證結論**：「Graph-Driven Development」當成一個**開發紀律的名字**找不到現成用法；
搜到的是圖文法驗證架構、知識圖譜生成架構方案、資料驅動架構——都是別的東西。
⇒ **整合沒有現成名字，零件全部有。兩件事都要誠實講。**

## 二、三個判準（任一破了，GDD 就不成立）

這三條是核心，其他都是為了守住它們。

「不成立」不等於「不准做」——破了要嘛改設計，要嘛**明寫「刻意這樣做，理由是 XX」讓知情的人決定**。
本節只負責把「破了」講得夠刺眼，不負責發放例外。

判準②只管插件邊界（新模組的註冊層），不套用在共用核心模組上——共用核心的必要變更
走你自己團隊的棕地安全改動流程去做知情決策。

1. **統一閘道只有一個。** 所有輸入從同一個講得出名字的地方進來，所有輸出從同一個地方出去。
   **出現第二個入口，就是耦合開始的那一刻。**
2. **加東西不動別層。** 在註冊層加一個新模組，其他層一個字都不用改。
   做不到就不是熱插拔，是硬接。
3. **正本只有一份。** 同一筆事實只有一個家，不同用途只是不同投影。
   出現第二份，「使用者隨時可以收回自己的資料」這種承諾當場變空話。

**第 3 條最常被違反，而且偽裝得最好**：它通常長成「另開一個新專案／新倉庫比較乾淨」。
乾淨的是程式，不乾淨的是資料——兩份使用者資料要想辦法不分裂，那個成本沒有便宜的做法。

## 三、施工前注意（開工前必答，缺一不准動工）

**G0｜有沒有一條已經走得通的最薄路徑？**
圖是橫著畫的（一層一層），**但不能照著橫著蓋**。開工前先問：
**現在有沒有一條真的從最外層走到最內層、會回東西的路？**（可以是假工具、假資料、stub 外部服務）
沒有 ⇒ **第一批就蓋它**，不要等到中段才第一次證明「接得起來」。

這一題防的失敗模式是每一層都做了八成、系統整體不能用——業界的真名詞是
**late integration（晚期整合）**，而 **Walking Skeleton** 這個做法存在的理由就是避免它
（Thoughtworks／Fowler 網站有案例）。
🔴 **骨架綠燈不等於產品可用**——它證明的是「接得起來」，不是「做完了」，兩件事要分開講。

**G1｜圖在哪？** 講得出路徑，且它是 **current-state**（現況），不是 target-state（設計藍圖）。
**設計藍圖不能冒充現況圖**——這是最常見的作假方式，因為兩者長得很像。

**G2｜圖是真的嗎？** 🔴 **不要讀它然後相信它。** 從圖裡挑**兩個**具體斷言，回程式碼實測：
一個「圖說有」的是不是真的存在，一個「圖說會這樣流」的是不是真的打一次、回應符合圖。
兩個都對才算查證過。任一不對 ⇒ **先修圖，再談施工**。

這兩個斷言只是抽樣煙霧測試，不是完整性證明——要下「沒有幽靈零件／全部接通」這種
否定結論，需要更完整的接線稽核（靜態 import／動態載入／事件匯流排／排程器／
呼叫端參數語意／鴨子型別注入點六條路都查），不能拿這兩個斷言充當。

**G3｜這批會動到哪幾條線？** 逐條列出：哪個模組對哪個模組、哪個方向、同步還是非同步、
對方掛掉時我方該排隊／降級／中止（失敗語意最常漏）。

🔴 **「不可繞過閘道」要寫成會紅的測試，不是靠人記得**：判準①這種規則，能寫成
**架構邊界測試**就不要留給人看守——業界的做法是把「A 必須經過 B」變成 CI 會跑的測試。
判準：**這條規則如果有人違反，是什麼東西會變紅？答不出來，它現在就只是期望。**

**G4｜三個判準這批破了哪一條？** 逐條對照第二節。破了要嘛改設計，
要嘛**明寫「刻意這樣做，理由是 XX」讓知情的人決定**——不能悄悄破掉。

**G5｜這批要同批改圖的哪幾行？** 寫下行號區間。寫不出來代表 G3 還沒想清楚。

## 四、審計閘門（收工前）

**A1｜圖跟程式對帳。** 這批動過的每一條線，逐條回圖上確認已更新。
不是「我有改圖」，是「改對了」——拿改完的圖再跑一次 G2 的兩個實測斷言。

**A2｜統一閘道還是只有一個嗎？** 搜這批有沒有新增繞過閘道的路徑。
下否定結論（「沒有第二個入口」）一律附**搜尋範圍與命中數**，並放**陽性對照**
（餵一個已知存在的入口字串，也回空 ⇒ 是工具壞了不是真的沒有）。

**A3｜拔掉一個模組，系統還活著嗎？** 熱插拔的可執行判準：
把這批新加的模組從註冊處移除，**其他層的測試必須全綠**。
有測試跟著紅 ⇒ 不是熱插拔，那條紅線就是耦合的位置。

🔴 **這一題只問「拆不拆得乾淨」，不問「它到底有沒有被用到」。**
後者是另一個觀察：拔掉之後，**這個模組自己的驗收必須變紅**；沒變紅就是幽靈。
兩件事要在同一次拔除演練裡一起看——只記得其中一件，會把「其他測試全綠」
同時讀成好事（拆得乾淨）和壞事（它是幽靈）。完整兩問見
[`three-track-checklist.md`](./three-track-checklist.md) 軌三。

**A4｜正本還是一份嗎？** 這批有沒有讓同一筆事實多了第二個家（含快取、鏡像、匯出檔被回讀）。

**A5｜機關真的在執法嗎？** 🔴 **這一題最常被跳過，而它是 GDD 與「掛牆上的圖」的唯一分界。**
逐項實測，不看設定檔字面：
1. 這個專案在你自己的受管專案名單裡嗎？
2. 這個倉庫有沒有裝上對應的 commit hook？（**登記進名單不等於受保護**——
   登記了卻沒真的安裝上，是個容易被漏掉的落差。）
3. **拔除演練**：改一個核心接線檔、不改圖、送進檢查 ⇒ **必須被擋**。
   沒擋就是沒裝好。演練完還原，版本控制狀態要回到乾淨。

**A6｜每一條裁決都有承接批次嗎？** 裁決下了、寫進正典了，**不等於有人會蓋**。
收工前對每一條新裁決搜一次施工排程：**搜得到承接它的批次代號嗎？** 搜不到 ⇒
那條裁決上線時不會存在。搜尋要附範圍與命中數，並放陽性對照（餵一個確定存在的
代號，證明檔案搜得到）。

## 五、`enforced_by`（誠實標示，別宣稱做到了沒做到的事）

| 規則 | 機械擋得住嗎 |
|---|---|
| 改核心接線檔必須同批改圖 | 🟡 大部分常見情境會擋，仍有已知漏網情境（細節見文末〈收錄時的兩處刪節〉，不在此公開） |
| 不准另開第二份同類地圖 | 🟢 可以做到真的擋 |
| 派工單要寫下這批怎麼驗（含 GDD 那一格） | 🟡 只驗「有沒有寫」，不驗寫得對不對——字數／關鍵字命中是代理指標，
代理指標一定可以被滿足而不滿足本體（例如塞一句「TDD：123456」就能穿過只認關鍵字的檢查）。
「三軌答得對不對」沒有機械答案，把關者只能是人。 |
| **圖的內容是不是真話** | 🔴 沒有腳本判得了。把關者是 G2／A1 的實測。 |
| **三個判準有沒有真的守住** | 🔴 判斷題。把關者是 G4／A2～A4。 |
| **這條線該不該存在** | 🔴 設計判斷，不是機械判斷。 |

🔴 **`git commit --no-verify` 可以整段跳過 commit 檢查。** 這是 Git 本身的固有性質，
任何機制都擋不住有權限的人蓄意繞過。**這道防線防的是忙中忘記，不是蓄意繞過**——
審計時不要用「能不能被繞過」的對抗式標準要求它。

## 六、與 BDD／TDD 的關係（三軌問不同的「對」）

| 軌 | 問什麼 | 失敗長什麼樣 |
|---|---|---|
| **TDD** | 零件本身對不對 | 永遠綠的測試——拔掉實作也不紅 |
| **BDD** | 使用者真的拿到了嗎 | 一批零件測試全綠，而正式流程裡零呼叫端（真實發生過的案例） |
| **GDD** | 圖是不是真的 | 圖描述了一個已經不存在的系統，而沒有任何東西會發現（真實發生過的案例） |

三題可以一個綠兩個紅，所以要分開問。合併成「有沒有測試」就會漏掉另外兩軌。

## 七、起因案例（改寫去識別化版，這段是這份文件存在的理由）

某個已經上線、正在被大量疊加新功能的專案，回頭用 GDD 三問一查，三件事全部不及格：

1. **圖過期了**：接線圖描述的是一種舊的資料存取方式，而那一層當天已經整層改掉，
   行為完全不同了。
2. **這個專案根本不在既有稽核機制的管轄名單裡。**
3. **連機關本身都沒有安裝**——該倉庫沒有裝對應的 commit hook。

⇒ 三個洞疊起來：**圖過期了、沒人會發現、也沒有東西會擋**，而同一時間正要在它上面
蓋大量新東西。

更值得記的是背後的共同病灶：當時有好幾支各自獨立的檢查機關，**剛好都因為範圍設定
得太窄，同時把正在進行的工作漏檢**——這不是巧合，是同一種失效形狀反覆出現：
**範圍縮小，包裝成「嚴謹的過濾條件」。** 治法不是再蓋第四支閘門，是在「每一批派工都
必經」的那一個節點補一題，而不是靠一份又一份的專案名單去圈範圍。

**另一則同一天發生的教訓**：一項決策已經拍板、也寫進了正式文件，但**施工排程裡搜不到
任何一批任務對應到它**——這代表上線的時候，這條決策事實上不會存在，因為沒有人被
指派去執行它。這正是本包〈裁決登記簿〉模板要解的病：**正典裡寫了，不等於有人會蓋。**
一個相關的推論是：**改東西的時候，如果只更新了說明用的投影，卻沒有動到真正的正本，
修正反而會輸給錯誤**——因為多數人只讀投影，不會回頭讀正本。判準是：
**改完之後問一句「如果有人只讀正本、不讀這份說明，他會拿到哪個版本？」**

## 八、這份文件刻意不做的事

- **不給「藍圖保存期限」這種數字。** 外部查證找不到「設計文件有效期」是業界正式概念，
  也沒有任何天數公式。要主張「先畫少一點」，理由是**先畫的那份會被實作揭露的問題推翻**，
  不是因為它到期了。
- **不重複別的方法論**（馬尾判斷梯、棕地安全改動、開工准入檢查）——那些各自有自己的文件，
  重複抄一份只會漂移走樣。
- **不畫圖給你。** 畫圖是判斷工作，不是模板工作；這份文件只規定圖要滿足什麼條件。
- **不管「這條線該不該存在」。** 那是架構設計判斷，不是本文件的範圍。
- **不給總分。** GDD 沒有分數，只有「三個判準有沒有破」與「機關有沒有在執法」。

### 收錄時的兩處刪節

為了符合這個公開工具包「零真實專案內容、不揭露具體解鎖方式」的規矩，原文有兩處
做了改寫，如實記錄在這裡：

1. **第七節的案例**原文指名了一個具體專案，這裡改寫成去識別化版本，只保留教訓本身。
2. 原文第五節有一段記錄一個尚未修好的具體繞過方法——公開具體怎麼操作等於教人怎麼
   繞過檢查，因此**不揭露操作方式本身**，只誠實留下天花板：
   **這一類機關目前有已知的漏網情境，還沒有全部堵住，已經記在對應專案自己的
   待辦清單裡等待修復。** 判準是「這句話是幫使用者知道天花板，還是幫他跳過天花板」——
   上面這句話只做前者。
